3. Multi-domínio / Multi-VLAN ⭐

Pré-requisito desta seção: máquina conectada a pelo menos duas redes diferentes (duas NICs físicas, ou uma NIC + VPN, ou uma NIC + Hyper-V/WSL). Se você só tem uma, pule para a seção 4.
T3.1Endpoint /network/interfaces detecta TODAS as NICs ativasnovo
curl http://127.0.0.1:8000/network/interfaces
✅ Esperado: JSON com uma entrada por NIC IPv4 que não seja loopback (127.x) nem APIPA (169.254.x). Cada uma com name, ip, cidr, mac.
T3.2Aba "Redes / VLANs" em Configuraçõesnovo
Abrir o app → Configurações. Confirmar que existem 4 abas: Scanner de Rede / Redes / VLANs / Acesso Remoto / Dados.
Clicar em "Redes / VLANs". Conferir os blocos:
  • Interfaces detectadas — mostra suas NICs locais. Botão "Importar" em cada.
  • Redes gerenciadas — vazio na primeira vez, com botão "Adicionar rede".
Clicar em "Importar" em cada NIC. Cada importação adiciona uma rede com nome = nome da NIC e source_ip preenchido.
Para cada rede importada, preencher (se aplicável):
  • Nome: ex. "Domínio A — VLAN admin"
  • DNS server: ex. 10.10.0.1
  • Domínio AD: ex. dominio-a.local
Clicar em Salvar Alterações. Recarregar a página → as redes persistem.
T3.3⭐ Ping com source_ip sai pela NIC corretaCRÍTICO
Abrir Wireshark. Filtrar por icmp. Selecionar a interface da NIC #1.
No app: Ferramentas → Ping. No dropdown "Sair pela rede", escolher a rede da NIC #1. Pingar 8.8.8.8.
✅ Esperado: Wireshark vê pacotes saindo. Source = IP da NIC #1.
Parar. Trocar para a NIC #2 no dropdown. Pingar de novo. Mudar Wireshark para a outra NIC.
✅ Esperado: agora os pacotes saem pela NIC #2.
T3.4Traceroute respeita source_ipnovo
Mesma ideia do T3.3, mas em Ferramentas → Traceroute.
✅ Esperado: a primeira linha do tracert mostra o gateway da NIC selecionada (não o gateway default).

Repetir trocando o dns_server para o do Domínio B:
✅ Esperado: agora retorna o IP do Domínio B. IPs diferentes confirmam que o resolver está consultando o servidor certo.

Em Ferramentas → Scanner de Rede: criar 2 abas. Em cada uma, escolher uma rede diferente no dropdown "Rede automática".
✅ Esperado: ao escolher uma rede, o CIDR auto-preenche (se estiver vazio).
Iniciar varredura nas duas abas em paralelo (com Wireshark observando).
✅ Esperado: pacotes ICMP de cada aba saem pela NIC correta. Resultados não se misturam.

Voltar ao Painel com hosts cadastrados.
✅ Esperado: hosts cujo IP cai dentro de uma rede cadastrada mostram um badge azul com o nome da rede ao lado do IP. Hosts que não batem em nenhuma não mostram badge.

T3.11Scanner identifica fabricante e tipo na sub-rede localnovo
Em Configurações → Scanner, confirmar que "Identificar fabricante no scan" está ligado.
Fazer um discovery na própria sub-rede (mesma VLAN do operador), onde haja máquinas Dell/HP/Lenovo/VMware, uma impressora e/ou uma câmera IP.
✅ Esperado: ao fim do scan aparece o status "Identificando fabricantes...". Os cards mostram o fabricante (ex.: "Dell Inc.", "Cisco Systems") abaixo do hostname.
✅ Esperado: cards ganham um rótulo de tipo (ex.: "Impressora", "Câmera IP", "Workstation Windows", "Equipamento de rede").
✅ Esperado: quando o tipo vem só de fabricante/hostname (incerto), aparece um ícone "?" ao lado; passar o mouse mostra o aviso "Tipo provável... pode estar incorreto". Tipos por porta forte (impressora 9100, câmera 554, RDP 3389) não mostram o "?".
Limitação esperada: o MAC só identifica fabricante, nunca o modelo. Nenhuma base no mundo mapeia MAC→modelo.
T3.12Scanner cross-VLAN: fabricante fica vazio (esperado)novo
Fazer um discovery em uma VLAN roteada (diferente da do operador), selecionando o source IP correto.
✅ Esperado: hosts são encontrados normalmente, mas fabricante fica em branco para a maioria — o MAC do destino não entra na tabela ARP local através do roteador. Isso é uma limitação do protocolo (ARP é L2), não um bug.
✅ Esperado: o tipo ainda pode aparecer quando há porta forte detectada (ex.: 9100 = Impressora), pois o port-probe funciona mesmo cross-VLAN.
T3.13Desligar identificação de fabricante acelera o scannovo
Em Configurações → Scanner, desligar "Identificar fabricante no scan" e Salvar.
Fazer um novo discovery na sub-rede local.
✅ Esperado: o status "Identificando fabricantes..." não aparece; cards não mostram fabricante (o tipo por porta ainda pode aparecer). Religar a opção restaura o comportamento.
T3.14Atualizar base de fabricantes (IEEE OUI)novo
Em Configurações → Scanner, no bloco "Base de fabricantes (IEEE OUI)", conferir o número de registros e a data de atualização.
Com internet disponível, clicar em "Atualizar base".
✅ Esperado: toast de sucesso com a contagem de registros (~38 mil). A data de atualização muda para hoje. O download é atômico (temp + rename): se cair no meio, a base antiga continua íntegra.
Repetir sem internet (ou rede sem saída/sem proxy).
✅ Esperado: toast de erro claro ("Erro ao atualizar..." / "Download incompleto"). A base local não é corrompida; o scan continua usando a base existente offline.
Cache vive em %APPDATA%\FerramentasDeRede\mac-vendors.txt (não mais em ~/.cache) — sobrevive ao portátil PyInstaller.
T3.15Abas de scan: renomear, fixar e persistirnovo
Em Ferramentas → Scanner de Rede, criar 2-3 abas com CIDRs diferentes.
Duplo-clique no título de uma aba.
✅ Esperado: o título vira um campo editável. Digitar um nome (ex.: "VLAN Servidores") + Enter renomeia. Esc cancela.
Passar o mouse sobre uma aba e clicar no ícone de pin.
✅ Esperado: a aba fica fixada (ícone de pin azul preenchido) e o "X" de fechar some — não dá para fechar por acidente. Clicar no pin de novo desafixa.
Fechar e reabrir o app.
✅ Esperado: as abas (com nomes e pins) voltam, igual aos cards de host. Resultados de scan antigos não voltam — cada aba reabre "Pronto" para re-escanear.
Persistência em localStorage versionada (chave scanSessions, v:1); JSON inválido é descartado sem quebrar a tela.

T4.2Polling com backoff quando backend cainovo
Com o app aberto, matar o processo do backend Python:
Get-NetTCPConnection -LocalPort 8000 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
No DevTools → Network, observar as chamadas /hosts e /network/monitor.
✅ Esperado: intervalos entre chamadas aumentam exponencialmente (2s → 4s → 8s → ... até 30s). Toast: "Servidor não responde. Tentando reconectar..."
Subir o backend de novo.
✅ Esperado: dentro de no máximo 30s aparece toast verde "Conexão com o servidor restaurada." e os pings voltam a ser de 2s em 2s.
T4.3Polling do cofre menos agressivobaixo
DevTools → Network. Filtrar por security/status. Aguardar 1 minuto.
✅ Esperado: aproximadamente 2 chamadas/min (era ~12/min antes).
T4.4Resolução DNS paralela no monitornovo
Em rede com DNS lento, monitorar 30+ hosts (preferencialmente com hostnames vazios).
Observar logs do backend (%APPDATA%\FerramentasDeRede\errors.log não, mas o stdout do Python — em dev é o terminal onde o app foi iniciado).
✅ Esperado: logs Reverse DNS Update: ... aparecem em rajada (várias por segundo) em vez de espaçados de ~2s. Ciclo completo de N hosts conclui em segundos, não minutos.

T4.5Memória estável após 30 minutosbaixo
Deixar o app rodando 30 minutos com monitoramento ativo. Anotar uso de memória do processo Electron no início e no fim (Task Manager).

T4.6Notificação de host caiu / voltounovo

✅ Esperado: quando o host cai (e cruza o critério "Smart Offline", não um ping isolado), aparece um toast vermelho "<host> ficou OFFLINE" E uma notificação nativa do Windows — mesmo com a janela do app minimizada / em segundo plano.

✅ Esperado: toast verde "<host> voltou ONLINE" + notificação nativa.

T4.7Histórico de disponibilidade persiste após restartnovo

✅ Esperado: o histórico anterior continua lá (antes era perdido — vivia só em memória). Host recém-adicionado mostra "ainda não há histórico" até o sampler rodar alguns minutos.

9. Troubleshooting

Backend não sobe / API offline
  1. Verificar log: %TEMP%\network_tools_debug.log
  2. Verificar porta presa: netstat -ano | findstr :8000
  3. Subir backend isolado pra ver o erro real: cd python && python -m api.server
"ModuleNotFoundError: No module named 'dns'"

Falta rodar pip install -r python/requirements.txt (T0.1). O dns_resolver.py tem fallback para socket, então a app não morre, mas as features de DNS por servidor específico não funcionam.

Aba "Redes / VLANs" não aparece em Configurações

Você está rodando uma build antiga. Certifique-se de que electron/dist/ foi regerado (npx vite build) e que está abrindo o app a partir do diretório principal.

Ping/traceroute "saem" sempre pela mesma NIC
  1. Confirmar que a rede tem source_ip preenchido em Configurações → Redes.
  2. Conferir no Wireshark antes de mexer (controle): qual é a NIC default.
  3. Rodar manualmente: ping -S <source_ip> 8.8.8.8 direto no cmd. Se isso também falhar, é problema de roteamento no Windows, não da app.
"TypeError: Cannot read properties of null"

Se aparecer com mensagens diferentes da do T3.7 (que foi corrigido), provavelmente é um campo novo do backend que veio null inesperado. Reportar com o stack trace e o ID do teste — fica fácil patchar.

Erro CORS no DevTools

O CORS agora só permite http://127.0.0.1:5173 e http://localhost:5173. Se você abriu a UI por outra origem, defina antes de subir o backend:

set NT_CORS_ORIGINS=http://outra-origem:5173
python python\main.py
